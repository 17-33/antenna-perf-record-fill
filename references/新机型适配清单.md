| 类别 | 具体项 | 在哪里改 |
|---|---|---|
| 结构 | 工作表名、行↔频点、列字母 | `scripts/_lib.js` 的 `SHEET_ALIASES` / `SHEET_STRUCT` / `RX_FREQS` / `TX_FREQS` |
| 机型参数 | σ、天线罩损耗、波导损耗、LNB NF、P | 填进 `fill_mark.js` 的 `spec.json`（或人工落表） |

## 1. 模板结构核对（先做，别跳）

```bash
node scripts/check_claims.js <目标记录表.xlsx>
```

看三件事：

1. **工作表匹配**——五张表是否都能按语义键找到。找不到的会打 `✗`，此时先改 `_lib.js` 里的 `SHEET_ALIASES`，把你们模板的实际表名加进别名数组。
2. **行 ↔ 频点**——每个有频点列的表会打印「最匹配的频点列（匹配 N / M 行）」。**必须出现 `✅ 与文档完全一致`**。
   出现 `⚠️ 与文档不一致` 就说明行序和 `SKILL.md` §2 不同，**必须按实际输出重定行号**，否则整批数据串行。
3. **跟踪精度**——该表没有频点列，脚本会明确打印"跳过频点对齐"，属正常，不要误判为失败。

```bash
node scripts/dump_xlsx.js <目标记录表.xlsx> <表名> --detail
```

用 `--detail` 看清：**哪一列是蓝底（`FF00B0F0` = 需填写）**、哪几格是公式（带 `ƒ`）、表头在第几行。
`--csv` 可以导出后丢进 Excel 筛。

> 实测提醒：本机那份 `VG180 天线电性能数据汇总(拓飞)-2026.09.03.xlsx` 的「方向图」表**不是** §2 布局
> （表头在第 1 行、数据横跨 B..BA、行 1~161）。`check_claims.js` 会如实报出不一致 —— 这正是它存在的意义。

## 2. 机型参数（每换一个机型/锅面，这些值都要重取）

| 参数 | 用在哪 | 来源 | 备注 |
|---|---|---|---|
| **σ 面型标准偏差** | EIRP `G4`、GT `F4` | 面型最佳拟合结果 | 合并单元格，**一台天线一个值**；同一批 EIRP/GT 各行共用 |
| **天线罩插入损耗 Lc** | EIRP `E`、GT `H` | IQC《天线罩插入损耗》**0 度均值行** | 表内无对应频点时取最近频点 |
| **波导/馈线损耗** | EIRP `F`（TX 段）、GT `E`（接收低频段） | 《QV 波段波导网络》检验报告 | **必须分频段取不同值**，不能全表一个数 |
| **LNB 噪声系数 NF** | GT `J` | LNB 供应商数据 | 大纲允许引用供应商数据；`Tr = 290(10^(NF/10)−1)` |
| **Tant** | GT `I` | 常量 **230 K** | T0 = 290 K |
| **P（BUC 正向功率）** | EIRP `J` | BUC 后台网页正向功率 dBm | `P(dBW) = dBm − 30`；**网页不显示频率，只能靠文件名定频点** |

派生量：

```
Lm(mm 计)   = 685.81 × σ² / λ²          （σ、λ 同单位）
λ(mm)       = 300 / f(GHz)
Lc + Lf     = 天线罩 + 面精度
L(feed)     = 波导/馈线损耗（分频段）
EIRP(dBW)   = P + G − L                 门限 ≥ 69
G/T(dB/K)   = (G − L) − 10lg(TA + Tr)   门限 ≥ 25
δ(°)        = √(δA² + δE²)              门限 ≤ 1/10 × 3dB 波束宽度
```

⚠️ **天线罩可能被重复扣减**：若方向图实测时已装罩，后续再扣 Lc 就是扣两次。口径问题，**报告里必须备注**。

## 3. 批次作业规范

**铁律：永不改动用户原始文件；只在副本/新文件上写；每批产出一个可回退的新文件。**

每一批的节奏：

```bash
# ① 建工作副本（原目录可能在只读位置，截图先复制进工作区）
# ② 判读：对每张图记录 —— 图类型 / CF（及换算后的射频）/ marker 表全部行 /
#           右上角注释 / 状态栏告警 / 时间戳（小字放大 ≥2× 核对）
# ③ 定位：按 行↔频点 、图表→列 、路径规则 得出单元格清单
# ④ 填值 + 标记
node scripts/fill_mark.js 原始记录.xlsx 填报版_批N.xlsx spec_batchN.json
# ⑤ 回读校验
node scripts/verify_mark.js 填报版_批N.xlsx 方向图 D5 E5 J5
node scripts/diff_sheets.js 上一版.xlsx 填报版_批N.xlsx 方向图 --soft
# ⑥ 回写：目标名被 Excel/WPS 占用时存成带后缀的新名（如 _批1-9.xlsx），
#         在回复里说明，不要反复重试
# ⑦ 汇总：每张图给"图名 → 行/列 → 值 → 来源"，并给全表进度表（哪些已填/还缺）
```

**spec.json 每批要写全的元信息**（`SKILL.md` §6 + §7）：

- `mark`：本批按图填写的格，全部改红字加粗 + 保留原蓝底
- `texts`：来源列（方向图 `U` / EIRP `L` / 跟踪精度 `D` / 前向链路 `F`）
- `notes`：批次日志行，写在表格下方空行，格式 `批次N｜日期｜源文件 → 已填 XX`

**重复投喂**：同一张图再次发来时用 SHA256 判重，**不重复填写**，但在日志里注明"与批次 N 同一文件"。
`fill_mark.js` 每次都会打印输出文件的 SHA256 与完整性校验结果，可直接留档。

**同名文件陷阱**：`39.95.jpg / 39.975.jpg / 40.jpg` 在 `LNB到频谱仪` 与 `LNB到测控基带XS05` **两个目录都有但内容不同**。
判据 = **电平**（−10~−12 → 前向链路 `B`；−20~−22 → `C`；−14~−16 → `D`）+ **仪表时间戳**（同一路径的截图时间戳是连续一串）。

## 4. 收尾重建定稿

清空版里公式会消失（§9.11）。所以**定稿不要从清空版长出来**：

1. 从**原始记录**重建一份干净副本；
2. 按批次顺序把全部批次 `spec` 串行回填（`fill_mark.js` 的 `input` 用上一步的 `output`）；
3. 公式列 `R/S/T`、`K`、`L/M`、`B15/B16/C17` 会自动长回来；
4. 全表复检：

```bash
node scripts/audit.js 定稿.xlsx 原始记录.xlsx --exempt-file=exempt.json
node scripts/diff_sheets.js 原始记录.xlsx 定稿.xlsx <表名> --soft
node scripts/zipcheck.js 定稿.xlsx
```

**`audit.js` 必须打印 `问题 0 项 ✅`**，四类口径全为"无"：

| 口径 | 定义 |
|---|---|
| 漏标 | 原表该格为空、本版有值，但未红字加粗 → 填了没留痕 |
| 错标 | 红字加粗但值为空且非公式 |
| 值不一致 | 两表都有值且不同，但本版未红字加粗 → **无痕改动，最危险** |
| 待填 | 蓝底格为空，或落在已知输入区且为空（**含无底色的前向链路输入格**） |

⚠️ 来源列与批次日志行属元信息格，会被判成"漏标"。用 `--exempt` 或 `--exempt-file` 排除，例如：

```json
{ "*": ["U2", "U3"], "方向图": ["A25:A40"] }
```

**反算闭环**（行、列判定都正确的最强证据）：某行方位 + 俯仰都齐了以后，用 `R/S/T` 公式手算 Gain，
应与原记录表 `T` 列**完全一致**。`analyze.js` 已经把这一步自动化了。

## 5. 三个最易犯的错

1. **按 marker 编号认列** → 必须按 **ΔdB 语义**认列。
   `M1` → `M` 列（绝对 dBm）；`≈−3 dB` → 3dB 列；`≈−10 dB` → 10dB 列；`−14~−18 dB` → 旁瓣列；`−20 dB 以下远区` → 不填。
   不同操作员编号习惯不同，**按编号认列是本流程最常见的出错原因**。

2. **拿接收图的 CF 当射频** → 接收类截图必须 `射频 = CF + 34.5 GHz`（本振）。
   37.5→3.0、37.75→3.25、38→3.5、39.95→5.45、39.975→5.475、40→5.5、40.025→5.525、40.05→5.55。
   填表用**射频**频点找行。

3. **跟踪精度取错字段** → 必须取 BAT Pro「**ANT 状态**」面板的**姿态**角，不是"传感器/编码器"角。
   同页传感器角波动大（实测 10 次波动 0.83°），**换字段会从合格变不合格**。这是口径问题，**必须让用户书面确认**。

## 6. 换机型后的自证

改完 `_lib.js` 的映射后，**至少**跑一遍：`dump` → `fill` → `verify` → `clear` → `audit` → `zipcheck`，
并确认 `check_claims.js` 全部显示 `✅ 与文档完全一致`。

若要连工具一起移植到别的运行时，按 `SKILL.md` §12.3 的六条实现规范做，
并用 `tests/selftest.js` 的等价断言逐条自证（正常样本必须 0 问题；人为破坏样本必须报错并非 0 退出）。
